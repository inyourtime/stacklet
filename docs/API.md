# API and backup contracts

Base path `/api/v1`. Same-origin only; Access authentication applies to every API route, including unknown routes. See `src/shared/contracts/index.ts` for executable Zod schemas.

## Generated documentation and Hono client

`GET /api/v1/openapi.json` serves OpenAPI 3.1 generated by `@hono/zod-openapi`. `GET /api/v1/reference` serves Scalar from `@scalar/hono-api-reference`. Both inherit the API authentication middleware, owner checks, origin restrictions, and no-store headers. These documentation routes return an OpenAPI document or HTML, rather than a data envelope.

Request and response schemas live in shared Zod contracts and are composed in `src/server/routes/contracts.ts`. Handlers use validated `c.req.valid(...)` inputs. Route registration is chained so `AppType` retains the complete RPC schema.

Frontend example:

```ts
import { hc } from "hono/client";
import type { AppType } from "../../server";

const client = hc<AppType>("/", {
  init: { credentials: "same-origin", cache: "no-store" },
}).api.v1;

const response = await client.summary.$get({ query: { month: "2026-11" } });

if (response.status === 200) {
  const { data, meta } = await response.json();
  console.log(data.month, meta.revision);
}
```

Use the app's `api` wrapper and `useOperation` for UI mutations so runtime response validation, idempotency retries, and captured dataset epoch remain consistent. Documentation requests go directly to the same origin; Scalar proxy and telemetry are disabled.

## Common response

```json
{
  "data": {},
  "meta": { "revision": 12, "datasetEpoch": "opaque-dataset-id" }
}
```

All financial responses use `Cache-Control: no-store`. Amounts are decimal strings (`"10000.00"`, `"0.00300001"`), never JSON floating point amounts. UUIDs identify entities; timestamps are UTC ISO 8601; trade dates are real `YYYY-MM-DD` calendar dates.

An error uses `{ "error": { "code", "message", "requestId" } }`. SQL and stack traces are never sent. A 401 or an Access login HTML response means reload/login is required.

## Mutation headers and concurrency

- `Content-Type: application/json` (DELETE may omit it)
- Browser same-origin `Origin` is required. Cross-site requests are rejected; no cross-origin CORS support.
- `Idempotency-Key`: 16–128 ASCII letters/digits/underscore/hyphen; a UUID is recommended. Generate once per submit, retain on retry. Use a new key for a different payload.
- `X-Dataset-Epoch`: use the epoch from the form's original data snapshot. Do not silently replace it while a form is open.
- PATCH, cash adjustments, and goal PUT include `expectedVersion` in the JSON body. DELETE uses `If-Match: "3"`.

All key checking and financial changes commit in one D1 batch. A completed key plus identical normalized input returns the original status and response, even after a later restore. A different input with that key returns `409 IDEMPOTENCY_CONFLICT`. Failed writes roll back their key claim.

`409 VERSION_CONFLICT` means refetch, show the conflict, and reopen/review the form. `409 DATASET_CONFLICT` means data was restored; reload before submitting again. No automatic overwrites.

## Endpoints

| Method | Route                            | Input / output                                                                             |
| ------ | -------------------------------- | ------------------------------------------------------------------------------------------ |
| GET    | `/summary?month=YYYY-MM`         | Current portfolio totals plus purchases for the selected month; default month uses Bangkok |
| GET    | `/cash-accounts`                 | Array of cash accounts with versions                                                       |
| POST   | `/cash-accounts`                 | `{name, balanceThb}` → `{cashAccount}`; 201                                                |
| PATCH  | `/cash-accounts/:id`             | `{name, expectedVersion}` → `{cashAccount}`                                                |
| POST   | `/cash-accounts/:id/adjustments` | `{mode, amountThb, expectedVersion}` → `{cashAccount}`; mode add/subtract/set              |
| GET    | `/transactions`                  | Filters `type`, `q`, `cursor`, `limit` → `{items, nextCursor}`                             |
| POST   | `/transactions`                  | Purchase input → `{transaction, affectedCashAccounts}`; 201                                |
| PATCH  | `/transactions/:id`              | Purchase input + expectedVersion → same response                                           |
| DELETE | `/transactions/:id`              | If-Match version → `{deleted:true, affectedCashAccounts}`                                  |
| GET    | `/btc-goal`                      | `{targetBtc, version, updatedAt}`                                                          |
| PUT    | `/btc-goal`                      | `{targetBtc, expectedVersion}` → `{goal}`; null clears target                              |
| GET    | `/backup`                        | Backup data envelope; headers described below                                              |
| POST   | `/imports/validate`              | `{backup}` → preview; read-only, no idempotency/epoch required                             |
| POST   | `/imports/replace`               | Restore input below → `{restored:true}` and new meta                                       |

Transaction fields:

```json
{
  "assetType": "btc",
  "assetName": "BTC",
  "tradeDate": "2026-11-11",
  "amountThb": "10000.00",
  "btcQuantity": "0.00300001",
  "cashAccountId": null,
  "note": null
}
```

assetType accepts stock, fund, btc, or gold. For stock/fund/gold, btcQuantity must be null; gold records cost in THB without a weight or quantity field. The transactions type filter and summary allocations also support gold. Cash account null means new money from outside the app. The app does not infer exchange rates or foreign currency balances.

Pagination sorts `trade_date DESC, id DESC`. Cursor is opaque; reuse it with the same filters. Limit defaults to 30, maximum 100. Search escapes literal `%`, `_`, and backslash. Escaped LIKE pattern including surrounding wildcards must fit D1's 50-byte limit; invalid queries return 400.

## Backup file

Save `data`, not the whole response envelope:

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-11-11T12:00:00.000Z",
  "cashAccounts": [
    {
      "id": "22222222-2222-4222-a222-222222222222",
      "name": "เงินลงทุน",
      "currency": "THB",
      "balanceThb": "40000.00",
      "createdAt": "2026-11-11T12:00:00.000Z",
      "updatedAt": "2026-11-11T12:00:00.000Z"
    }
  ],
  "transactions": [],
  "btcGoal": { "targetBtc": "1.00000000" }
}
```

Transactions include purchase fields plus id/createdAt/updatedAt. No versions, audit, internal metadata, or idempotency records are exported. Cash balances are final snapshot balances, not opening deposits.

## Restore handshake

1. Read file bytes (maximum 1 MiB), parse JSON, POST `{backup}` to validate.
2. Preview returns cashAccountCount, transactionCount, totalPrincipalThb, btcQuantity, targetBtc, fileHash, and snapshotRevision.
3. GET `/backup`, download its `data`. Its revision must equal the preview revision. The response includes `X-Backup-Restorable: true` and an `X-Backup-Receipt` signed for the revision/epoch, valid for 15 minutes.
4. User checks that the backup is saved and explicitly confirms replacement.
5. POST to replace with the same file, mutation headers, and:

```json
{
  "backup": {},
  "fileHash": "sha256-hex-from-preview",
  "snapshotRevision": 12,
  "backupReceipt": "signed-receipt-from-export"
}
```

Replacement repeats validation, verifies receipt/fileHash, then checks epoch and revision inside the atomic write. Conflict → no changes. Restore loads snapshots without purchase effects, creates opening audit baseline, checks counts/sums/goal, changes epoch and increments revision. Reload client caches after success.

Export can exceed import limits; then `X-Backup-Restorable: false`, no receipt is issued, and the UI explains the limitation. This also prevents replacing the current data without a recoverable pre-restore backup. The server cannot prove the browser finished saving a download.

## Boundaries

Money: max 1,000,000,000 THB per account/purchase; BTC/goal: max 21,000,000 per value. Purchase totals and combined balances must fit JavaScript safe integers in smallest units. More than two baht or eight BTC decimal places is rejected without rounding.

The dashboard fetches BTC/THB market prices directly from `https://data-api.binance.vision/api/v3/ticker/price?symbol=BTCTHB` every 60 seconds while open. This public request omits credentials and is separate from the authenticated API. Unrealized BTC profit/loss uses the current portfolio's BTC quantity and BTC allocation cost, with integer arithmetic and satang rounding. Quotes are not stored in D1 or backups and do not change principal totals or allocations.

No account deletion/archive API, sells, transfers, recurring jobs, or multi-user ownership are included in v1.
